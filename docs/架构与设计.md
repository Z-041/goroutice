## 分层架构

采用经典的四层架构，依赖方向自上而下：

```
handler（HTTP 处理） → service（业务逻辑） → repository（数据访问） → model（数据模型）
```

| 层 | 目录 | 职责 |
| --- | --- | --- |
| Handler | `internal/handler` | 解析请求、参数绑定、调用 service、统一响应 |
| Service | `internal/service` | 业务规则、事务编排、权限校验、错误映射 |
| Repository | `internal/repository` | 基于 GORM 的数据库 CRUD 与查询 |
| Model | `internal/model` | 数据表结构定义 |

其他支撑模块：

- `internal/pkg`：可复用的纯工具（密码哈希、JWT、分页、slug、token、响应、错误）。
- `internal/middleware`：Gin 中间件（认证、授权、限流、日志等）。
- `internal/authz`：Casbin 模型、策略种子与 GORM 适配器。
- `internal/config` / `internal/database`：配置加载与数据库初始化。
- `internal/router`：路由注册与中间件编排。

## 请求处理流程

1. **全局中间件**依次执行：`RequestID`（注入链路 ID）→ `BodyLimit`（限制请求体大小）→ `Logger`（结构化日志）→ `Recovery`（panic 恢复）→ `CORS`（跨域）。
2. 进入路由分组，按需执行：
   - `Auth`：解析并校验 JWT，将 `user_id`、`username`、`roles` 写入上下文。
   - `Authorize`：调用 Casbin 判断当前角色是否有权访问该路径与方法。
   - `RateLimiter`：令牌桶限流（写接口）。
3. Handler 绑定参数 → 调用 Service → 通过 `response` 统一返回 JSON。

## 认证机制

认证基于 **JWT（access token）+ Refresh Token 轮换**。

### 令牌类型

| 令牌 | 存储 | 时效（默认） | 用途 |
| --- | --- | --- | --- |
| access token | 客户端（无状态 JWT） | 15 分钟 | 接口鉴权 |
| refresh token | 服务端仅存哈希 | 30 天 | 换取新令牌对 |

### Access Token（JWT）

载荷 `Claims` 字段：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 用户 ID |
| `username` | 用户名 |
| `roles` | 角色列表 |
| `token_type` | 固定 `access`，防止其他令牌被误用 |
| `token_version` | 令牌版本，改密/全端下线后递增使旧令牌失效 |
| `iss` / `sub` / `exp` / `iat` | 标准 JWT 声明 |

签名算法为 `HS256`，密钥来自 `jwt.secret`。

### Refresh Token

- 随机字符串，服务端仅保存其 **SHA-256 哈希**（`refresh_tokens.token_hash`）。
- 刷新时校验哈希与过期时间，成功后 **轮换**：吊销旧 token 并签发新令牌对。
- 登出吊销单个；全端下线/改密/注销账号吊销全部。

### 认证流程

**注册**：校验用户名/邮箱唯一性 → 密码强度校验 → bcrypt 哈希 → 创建用户（默认 `user` 角色）→ 若开启邮箱验证则状态置「未验证」并发送验证邮件。

**登录**：检查是否被锁定 → 按用户名或邮箱查找 → 校验密码 → 校验状态（禁用/未验证拦截）→ 签发令牌对。

**主动失效**：修改密码、重置密码、全端下线时递增 `token_version`，使所有已签发 access token 失效；同时吊销全部 refresh token。

### 密码与账户安全

- **密码哈希**：bcrypt。
- **密码强度策略**：可配置最小长度、是否强制大写/特殊字符（`security.password_*`）。
- **登录失败锁定**：连续失败达 `max_login_attempts` 次后锁定 `login_lock_minutes` 分钟（内存实现，按账号维度）。
- **防枚举**：忘记密码接口对未注册邮箱静默成功，登录统一返回「账号或密码错误」。

## 授权机制（RBAC）

基于 Casbin，将角色（`sub`）对路径（`obj`）执行 HTTP 方法（`act`）的权限建模：

```text
[request_definition] r = sub, obj, act
[policy_definition]  p = sub, obj, act
[role_definition]    g = _, _
[matchers] m = g(r.sub, p.sub) && keyMatch2(r.obj, p.obj) && regexMatch(r.act, p.act)
```

- `keyMatch2` 支持 `:id`、`*` 路径通配；`regexMatch` 支持方法正则（如 `(GET|POST|PUT|DELETE)`）。
- 策略持久化在 MySQL `casbin_rule` 表（通过自定义 GORM 适配器）。
- 角色继承：`admin` 继承 `author`，`author` 继承 `user`。

### 默认策略

| 角色 | 权限 |
| --- | --- |
| `user` | 个人中心：`GET/PUT /api/v1/auth/profile`、`PUT /api/v1/auth/password` |
| `author` | 文章与文件：`POST/PUT/DELETE /api/v1/articles/:id`、`GET /api/v1/me/articles`、`POST/GET/DELETE /api/v1/files` |
| `admin` | 管理端全部：`/api/v1/admin/*`（所有方法） |

权限策略、角色继承、用户角色均可在运行时通过管理接口动态调整，并记录审计日志（`permission_audits`）。审计由 `AuditService` 统一写入：认证事件（注册、登录成功/失败、改密/重置密码等）在 `AuthService` 内记录，管理端写操作（用户/分类/标签/文章/文件）在 handler 层记录，动作常量定义于 `model/audit.go`。审计为旁路能力，写失败不影响主流程。

## 中间件

| 中间件 | 文件 | 职责 |
| --- | --- | --- |
| RequestID | `middleware/requestid.go` | 生成/透传请求 ID，写入响应头与日志 |
| BodyLimit | `middleware/bodylimit.go` | 限制请求体大小 |
| Logger | `middleware/logger.go` | 结构化请求日志（含耗时、状态码） |
| Recovery | `middleware/recovery.go` | panic 恢复，返回 500 |
| CORS | `middleware/cors.go` | 跨域配置 |
| Auth | `middleware/auth.go` | 解析 JWT，校验 token_type、版本与用户状态，注入上下文 |
| Authorize | `middleware/authorize.go` | 基于 Casbin 的路径/方法鉴权 |
| RateLimiter | `middleware/ratelimit.go` | 令牌桶限流（分档、多维分桶） |

## 接口限流

限流器为**分级令牌桶**，按 `档位 | 身份 | 接口` 三元组分桶计数：

- **档位（tier）**：默认档（认证类接口，`rps/burst`）与写档（全量写接口，`write_rps/write_burst`）。
- **身份（identity）**：已登录取 `user:<id>`，未登录取 `ip:<client_ip>`。
- **接口（route）**：路由注册路径（如 `/api/v1/auth/login`）。

写接口通过 `WriteHandler` 仅对 `POST/PUT/PATCH/DELETE` 生效，读接口不受写档限制；认证类接口（登录/注册等）使用默认档独立限制。超过阈值返回 `429`。

## 数据库表结构

启动时通过 `AutoMigrate` 自动创建/更新以下表（下划线命名）：

| 表 | 模型 | 说明 |
| --- | --- | --- |
| `users` | User | 用户（软删除） |
| `user_roles` | UserRole | 用户-角色多对多 |
| `categories` | Category | 分类 |
| `tags` | Tag | 标签 |
| `articles` | Article | 文章（软删除） |
| `article_tags` | — | 文章-标签多对多（GORM 自动生成） |
| `article_revisions` | ArticleRevision | 文章历史修订快照（`idx_article_revision`：`article_id` + `version`） |
| `files` | File | 上传文件元数据 |
| `permission_audits` | PermissionAudit | 审计记录（认证事件 + 管理端写操作） |
| `refresh_tokens` | RefreshToken | refresh token 哈希 |
| `email_verifications` | EmailVerification | 邮箱验证令牌 |
| `password_resets` | PasswordReset | 密码重置令牌 |
| `casbin_rule` | CasbinRule | Casbin 策略（自定义表名） |

### 关键字段说明

- **主键**：所有业务模型使用 UUID 字符串（`Base.ID`，`BeforeCreate` 自动生成）。
- **软删除**：`users`、`articles` 使用 `gorm.io/plugin/soft_delete`，唯一索引与 `deleted_at` 组合以支持同名复用。
- **唯一约束**：用户名/邮箱（含软删除）、分类/标签 `name` 与 `slug`、文章 `slug`。
- **令牌安全**：刷新、邮箱验证、密码重置三类令牌一律只存 SHA-256 哈希（刷新令牌用 `token_hash` 列，后两者列名保留 `token`），明文只出现在发给用户的邮件里，库或备份泄露无法直接用于登录/激活；敏感字段不参与 JSON 序列化。改密/重置密码会**在同一事务内**更新密码、递增 `token_version` 并吊销全部 refresh token。
- **全文索引**：`articles` 上的 `ft_article`（`title, summary, content`）不走 `AutoMigrate`，由启动时的 `EnsureArticleFulltextIndex` 用 `CREATE FULLTEXT INDEX ... WITH PARSER ngram` 单独创建（中文必须用 ngram，默认解析器会把整段中文切成一个巨型 token，检索永远命中不到）。
- **修订快照**：`article_revisions` 存的是「更新发生前」的整份文章状态（含正文与逗号分隔的 `tag_ids`），非 diff；写入与文章更新在同一事务内完成，版本号用 `MAX(version)+1` 分配，超出 `article.revision_keep` 的旧版本按 `version` 升序裁剪。
